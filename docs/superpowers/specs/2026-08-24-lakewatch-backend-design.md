# Lakewatch output format for the Databricks Sigma backend — design

Date: 2026-08-24
Status: approved for planning

## Goal

Add a `lakewatch` output format to the existing `DatabricksBackend` so that a Sigma
rule can be converted directly into a Lakewatch detection rule (`kind: Rule` YAML),
the same document shape the Lakewatch API/UI and `lakewatch apply` consume.

Assumption: rules are first normalized to OCSF by the
[`SigmaHQ/pySigma-pipeline-ocsf`](https://github.com/SigmaHQ/pySigma-pipeline-ocsf)
processing pipeline (source also available locally at `../pySigma-pipeline-ocsf`),
so field names and injected conditions are already OCSF-shaped when this format runs.

## Requirements (from the request)

1. A Sigma rule produces a Lakewatch rule; a 1:1 relationship between input rule and
   output document.
2. The table name may be supplied via a backend option (`-O table_name=…`). When it is
   not supplied, derive it from what the OCSF normalization provides.
3. Batch rules are generated by default.

## Key decisions (confirmed with the user)

- **Table resolution:** derive from the OCSF `class_uid` / `type_uid` / `class_name`
  that the OCSF pipeline injects (not from a private logsource→table map).
- **Output packaging:** multi-document YAML — one `---`-separated `kind: Rule`
  document per converted query, in a single `sigma convert` output. (pySigma backends
  cannot emit one OS file per input file; multi-doc YAML is the idiomatic 1:1
  representation and is what Lakewatch tooling accepts.)
- **Input mode:** batch only in v1. Streaming is out of scope (documented as future work).
- **Metadata:** best-effort mapping from Sigma fields, with `-O` overrides for the
  Lakewatch-required fields Sigma does not carry (fidelity, category), plus a bundled
  MITRE technique-ID → name lookup.

## Where it lives

All changes are in the existing package — **no new package**:

- `sigma/backends/databricks/databricks.py`
  - add `"lakewatch"` to the `formats` ClassVar dict;
  - add `finalize_query_lakewatch(rule, query, index, state)`;
  - add `finalize_output_lakewatch(queries)`;
  - extend `__init__` with new keyword options (below);
  - add a module-level OCSF `class_uid → gold-table` map and a MITRE technique map
    (a separate module, e.g. `sigma/backends/databricks/lakewatch_maps.py`, to keep
    `databricks.py` focused).
- `tests/test_backend_databricks_sigma.py` (or a new `test_lakewatch_databricks_sigma.py`).
- `README.md` — a "Lakewatch output" section mirroring the `detection_yaml` docs.

This reuses the existing format mechanism exactly as `dbsql` and `detection_yaml` do:
the backend produces the boolean predicate as `query`, and `finalize_query_*` wraps it.

## Backend options (`-O key=value`, arriving as `__init__` kwargs)

| Option | Default | Meaning |
|--------|---------|---------|
| `table_name` | *(none)* | Overrides table resolution for **all** rules in the run. |
| `lookback` | `25 HOUR` | Batch time-window predicate, in **Spark SQL interval** syntax: `time >= CURRENT_TIMESTAMP() - INTERVAL <lookback>`. Default gives a 1h overlap over the 24h schedule so window boundaries don't drop events. |
| `schedule` | `24h` | `spec.schedule.atLeastEvery`, a **Lakewatch duration** string. Separate knob from `lookback` (different syntaxes on purpose). |
| `compute_group` | `automatic` | `spec.schedule.computeGroup`. |
| `default_fidelity` | *(derived from status)* | Fallback / override for `spec.metadata.fidelity`. |
| `default_category` | `Static Signature` | `spec.metadata.category`. |

`lookback` is a Spark interval literal (`24 HOUR`, `13 HOUR`, `7 DAY`) dropped verbatim
after `INTERVAL`. `schedule` is a Lakewatch duration (`24h`, `12h`, `1d`) passed verbatim
to `atLeastEvery`. They are intentionally distinct so each lands in the right dialect.
Existing options (`raw_log_field`, etc.) are unaffected.

## 1. Table resolution

Precedence, per rule:

1. If `table_name` option is set → use it.
2. Else inspect the **transformed** rule (`rule.detection.detections`, post-pipeline) for
   a detection item whose field is `class_uid`, `type_uid`, or `class_name`:
   - `class_uid` → map directly;
   - `type_uid` → `class_uid = type_uid // 100`, then map;
   - `class_name` → normalize to snake_case only (lower-case, runs of non-alphanumerics
     → single `_`, e.g. `"API Activity"` → `api_activity`, `"HTTP Activity"` →
     `http_activity`, `"Detection Finding"` → `detection_finding`). **Do not strip
     "activity"** — the gold-table names keep it (`api_activity`, `dns_activity`,
     `process_activity`, …). Accept the result only if it is in the known gold-table set;
   - resolve via the `OCSF_CLASS_UID_TO_TABLE` map below.

   The gold-table name is the OCSF class name in snake_case, so the normalized
   `class_name` and the `class_uid`-mapped name agree by construction. When both a
   `class_uid`/`type_uid` and a `class_name` are present, `class_uid`/`type_uid` wins
   (numeric, unambiguous); `class_name` is the fallback for pipelines that emit only a name.
3. Else → raise `SigmaConversionError` naming the rule title and instructing the user to
   pass `-O table_name=…`. (No bogus table is ever emitted.)

Rationale for reading the parsed rule rather than string-parsing the SQL: the injected
condition is a structured `SigmaDetectionItem`, so extraction is exact and quoting-agnostic.

### `OCSF_CLASS_UID_TO_TABLE` (grounded in the skill's `gold_tables.md` — 22 tables)

```
1001 file_activity            3001 account_change          4004 dhcp_activity
1006 scheduled_job_activity   3002 authentication          4007 ssh_activity
1007 process_activity         3004 entity_management        4009 email_activity
1009 script_activity          3005 user_access             6003 api_activity
2002 vulnerability_finding    3006 group_management         6004 datastore_activity
2004 detection_finding        4001 network_activity         6005 file_hosting_activity
2005 incident_finding         4002 http_activity
2006 data_security_finding    4003 dns_activity
```

Class UIDs the current OCSF pipeline emits that have **no** gold table (→ fall through to
`-O` / error): `6002` (Application Lifecycle), the registry classes, Windows service
classes, and any malformed pipeline `type_uid` values (e.g. `3002001`). This limited
coverage is a property of the current pipeline's category set, not of our map; the full
22-entry map lets cloud/AWS OCSF pipelines that emit `api_activity`, `authentication`,
etc. resolve cleanly.

The injected `class_uid = …` / `type_uid = …` predicate is **left in** the generated
`WHERE` clause in v1 (it is a valid gold-table column and harmless). Stripping it as
redundant is noted as future work.

## 2. Batch SQL construction

```sql
SELECT *
FROM <resolved_table>
WHERE time >= CURRENT_TIMESTAMP() - INTERVAL <lookback>   -- default: 25 HOUR
  AND (<query>)
```

- `<query>` is the backend's boolean predicate (unchanged from other formats).
- `SELECT *` combined with `spec.output.defaultContext: true` records all input-row
  fields on the notable (matches the skill's batch examples).
- Empty `<query>` (e.g. unsupported rule) → the query is skipped in output assembly.

## 3. Metadata mapping

Produced document (field order preserved via `yaml.dump(sort_keys=False)`):

```yaml
apiVersion: v1
kind: Rule
metadata:
  displayName: <rule.title>
  comment: <rule.description or rule.title>          # short summary
spec:
  input:
    batch:
      sql: |-
        SELECT * FROM <table> WHERE time >= ... AND (<query>)
  metadata:
    objective: <rule.description or rule.title>       # long form
    severity: <mapped from level>
    fidelity: <mapped from status or -O override>
    category: <-O default_category, else "Static Signature">
    mitre:                                             # only if attack.* tags present
    - taxonomy: Enterprise
      tactic: <tactic name from attack.<tactic> tag>
      technique: <name from bundled ID→name map>
      techniqueId: T####
      subTechnique: <name or ''>
      subTechniqueId: <T####.### or ''>
  output:
    summary: <rule.title>
    defaultContext: true
  schedule:
    atLeastEvery: <schedule>
    computeGroup: <compute_group>
    continuous: false
    enabled: true
```

`metadata.name` (the `rl-xxxxxxxx` id) is **omitted** so the server mints a new one.

### Severity: Sigma `level` → Lakewatch `severity`

| Sigma level | Lakewatch severity |
|-------------|--------------------|
| critical | Critical |
| high | High |
| medium | Medium |
| low | Low |
| informational | Informational |
| *(none)* | Medium (default) |

### Fidelity: Sigma `status` → Lakewatch `fidelity` (overridable by `-O default_fidelity`)

| Sigma status | Lakewatch fidelity |
|--------------|--------------------|
| stable | High |
| test | Medium |
| experimental | Investigative |
| *(other/none)* | Development |

### Category

`-O default_category` if set, else `Static Signature`. (Sigma does not carry the
detection-methodology concept; aggregation rules that would be `Statistical` are left
to the user via `-O`.)

### MITRE ATT&CK: from Sigma `tags`

Parse `attack.*` tags on the rule:
- `attack.<tactic>` (e.g. `attack.execution`) → `tactic` (title-cased words).
- `attack.t1059` → `techniqueId: T1059`; `attack.t1059.001` → `techniqueId: T1059`,
  `subTechniqueId: T1059.001`.
- Resolve `technique` / `subTechnique` names from a **bundled static ID→name table**
  (`MITRE_TECHNIQUES` in `lakewatch_maps.py`), generated from MITRE ATT&CK STIX data as a
  one-off dev step and committed. Rationale: authoritative names with **zero runtime
  dependencies** and offline/CI-friendly conversion — the `mitreattack` package was
  rejected for v1 because it pulls in `stix2`/`taxii2-client`/`pandas` and a ~30 MB STIX
  bundle for what is a dict lookup. (If names ever need to auto-track new ATT&CK releases,
  or tactic-from-technique inference is wanted, revisit `mitreattack` then.)
- Unknown IDs → emit the ID with an empty name rather than dropping the mapping.
- No `attack.*` tags → omit the `mitre` block entirely (it is optional in Lakewatch).

## 4. Output assembly

`finalize_output_lakewatch(queries)`:
- Each element of `queries` is the JSON-serialized per-rule dict produced by
  `finalize_query_lakewatch` (same intermediate-JSON approach as `detection_yaml`, so
  status filtering happens in one place).
- Skip entries whose status is `deprecated`/`unsupported` or whose SQL is empty.
- Emit each surviving rule as its own YAML document, joined with `\n---\n`, via
  `yaml.dump(doc, sort_keys=False, default_flow_style=False)`.

## 5. Testing

New tests parallel to the existing backend tests:

1. `-O table_name=my_table` → SQL uses `FROM my_table`.
2. Rule run through the local OCSF pipeline (`process_creation`) → table derived as
   `process_activity`; `type_uid // 100` path exercised.
3. `dns` category (direct `class_uid 4003`) → `dns_activity`.
4. Batch SQL shape: `SELECT * FROM … WHERE time >= CURRENT_TIMESTAMP() - INTERVAL 25 HOUR AND (…)`.
5. Severity + fidelity + category mapping (including `-O` overrides).
6. MITRE mapping from `attack.execution` + `attack.t1059.001`.
7. No resolvable table and no `-O table_name` → `SigmaConversionError`.
8. Multi-document output: two rules → two `---`-separated documents.
9. `-O default_category` / `-O default_fidelity` overrides.

Coverage stays within the existing pytest + coverage setup. README gains a "Lakewatch
output" section with CLI (`sigma convert -t databricks -f lakewatch -p ocsf …`) and
programmatic examples, and lists the `-O` options.

## Out of scope (future work)

- Streaming rules (`spec.input.stream`, `tables:`/watermark).
- `observables` generation (Sigma does not describe observables cleanly).
- Stripping the redundant injected `class_uid`/`type_uid` predicate from the `WHERE`.
- Per-OS-file output (would require a separate CLI wrapper; multi-doc YAML covers v1).
- `Statistical`/aggregation category auto-detection.
